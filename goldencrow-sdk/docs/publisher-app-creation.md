# Publisher app creation

Runtime `branding.colors` preserves `advancedConfiguration.semanticColors` when supplied, or the existing nine-color semantic derivation otherwise, and appends each normalized `config.colors.counterpointClockwise` / `config.colors.counterpointAnticlockwise` only when available. The nine semantic fields remain required; both counterpoints are optional six-digit hex fields in the runtime producer type and OpenAPI response contract. A missing counterpoint is omitted without synthesizing a replacement, allowing native clients to retain canonical purple `#8A4BF7` or cyan/turquoise `#19D7E1`. Manual light/dark `colorOverrides` retain priority.

An existing runtime-enabled app (`active` or `active_for_testing`) is republished atomically on its first runtime read after this contract update: `runtimeRevision` increases by one and the server-only `runtimeColorContractVersion` publication marker is stored in `app_configs`. Internal color contract 3 covers the OKLCH defaults for historical records missing counterpoint seeds. New activations and subsequent enabled saves already publish the current contract. Publisher exports, GOD MODE exports, and public runtime reads share this publication check, so repeated reads keep the same revision. The existing SHA-256 response ETag changes with the new payload; an old `If-None-Match` receives the corrected JSON, while a current ETag receives 304. The marker is neither an editor input nor a runtime response field.

The shared visual identity editor has three draft sections: general identity, three main colors, and four counterpoints. A custom counterpoint stays fixed when the primary changes; automatic ones follow the existing hue calculation. Restoring an automatic value uses the current primary. Only Apply requests the override plan and commits the resulting palette to the form; Cancel discards the draft, and a failed calculation leaves the previously applied palette intact. The normal app save persists these applied choices.

Automatic palette application stores its automatic result separately in optional `advancedConfiguration.generatedColorOverrides`. The next application compares each current light/dark value with that saved baseline: unchanged generated values are recalculated, manual values and alpha are retained, and an explicitly removed generated appearance continues using its native fallback. Contrast is checked again after merging manual edits: automatic ink or gradient stops adapt around locked manual values, and those automatic corrections enter the baseline. An impossible combination of locked colors fails Apply without overwriting those colors. This provenance is validated and persisted with the editor configuration, but is never included in the mobile runtime JSON. Existing apps without provenance recognize exact results from the frozen v5 calculator and from the current calculator under their previous palette; unknown values remain manual. Historical HSL accessory defaults are also recognized when an older configuration omitted counterpoint seeds.

Manual counterpoints use the existing four camelCase fields under `colors`, with no extra persistence flags. Request validation, palette planning, SDK normalization, stored reads and runtime export preserve supplied values. Missing counterpoints receive OKLCH hue rotations of the primary, preserving its lightness and chroma with chroma-only gamut mapping. Neutral identities stay neutral. Runtime continues exposing only the two declared near counterpoints; far counterpoints supply their existing tonal override flows.

Both creation wizards and the edit screen share catalog v8 (698 roles, 21 declared contrast relationships). Synchronize the complete native source and SDK allowlist together with `node scripts/sync-publisher-app-color-catalog.mjs [path-to-CUSTOM_APP_COLORS.json]`. Each light/dark family is transformed continuously: relative hue spacing and chroma ratios are retained, shade lightness changes monotonically around its anchor, and environmental backgrounds, lighting and functional ink retain their original lightness. Generated anchors reserve shade headroom for black/white seeds; explicit base colors remain exact. Quiet modes and semantic states are protected independently, deep dark foundations remain native, and unchanged modes are omitted so platform-specific defaults and exact native opacity survive. Illustration destinations keep their native brand/counterpoint resolver unless manually overridden. Automatic foreground contrast checks composite alpha over the group canvas and sample gradient interiors; when necessary, a whole gradient is adjusted together. Manual overrides are merged afterwards without modifying their values.

The backoffice publisher and GOD MODE creation wizards run four ordered operations after terms acceptance: create the base app, calculate the palette overrides, update the app with the full advanced configuration, and create its testing identifier. The final identifier command sets new apps to `active_for_testing`; it never promotes a newly created app to `active`. One progress dialog reflects completed responses. Retries retain acknowledged checkpoints; palette, update, or identifier failures do not create another app or publish an incomplete configuration.

`active_for_testing` and `active` both allow runtime access, catalog availability, identifier reuse, revision updates and deactivation. They remain distinct persisted statuses and review choices. Existing active apps retain their status, including when a legacy identifier is replaced. New catalog snapshots include a separate testing count; older snapshots with the original five status counts remain readable with a zero testing count. Runtime JSON retains its existing `published` status.

GOD MODE uses `POST` / `PUT /admin/publisher-app-configs/organizations/:organizationId` and `POST /admin/publisher-app-configs/organizations/:organizationId/identifier`. All three commands require bootstrap access. The publisher portal uses its existing scoped `/publisher-app/config` commands. Updates preserve the original terms acceptance and audit identity.

`custom_apps_snapshot/simple` keeps the existing catalog schema and `image` field, but newly written catalog images are HTTPS references rather than embedded data URLs. Each inline image is stored once in `custom_app_icons/{sha256}`, with exactly `contentType` and `base64` string fields. The hash is SHA-256 of the original complete data URL; documents are immutable by content identity and bounded by the existing 900,000-character image limit. Original app and publisher icon fields stay intact.

Incremental catalog transactions compact every legacy inline image and write the referenced icon documents atomically with the catalog update. Full snapshot refreshes persist deduplicated icons in bounded groups before writing the compact catalog. This prevents accumulated images from exceeding Firestore's aggregate document limit.

`GET /publisher-app/icon?hash=<64 lowercase hex characters>` serves only those catalog icon bytes, with an immutable cache policy, cross-origin image embedding, MIME validation, hash verification, and a sandboxed content security policy. Missing hashes return 404 and invalid parameters return 400. App configurations and all app commands remain authenticated. No new Firebase project or storage bucket is required at startup.
