# Publisher app creation

Runtime `branding.colors` preserves `advancedConfiguration.semanticColors` when supplied, or the existing nine-color semantic derivation otherwise, and appends each normalized `config.colors.counterpointClockwise` / `config.colors.counterpointAnticlockwise` only when available. The nine semantic fields remain required; both counterpoints are optional six-digit hex fields in the runtime producer type and OpenAPI response contract. A missing counterpoint is omitted without synthesizing a replacement, allowing native clients to retain canonical purple `#8A4BF7` or cyan/turquoise `#19D7E1`. Manual light/dark `colorOverrides` retain priority, except the four Community quick-action text foregrounds, which are fixed opaque white in both appearances.

An existing runtime-enabled app (`active`, `active_for_testing`, `active_waiting_for_payment`, or `active_waiting_for_upload`) is republished atomically on its first runtime read after this contract update: `runtimeRevision` increases by one and the server-only `runtimeColorContractVersion` publication marker is stored in `app_configs`. Internal color contract 6 publishes fixed opaque-white text for the four Community quick-action tiles, including historical configurations with dark or translucent text overrides. New activations and subsequent enabled saves already publish the current contract. Publisher exports, GOD MODE exports, and public runtime reads share this publication check, so repeated reads keep the same revision. The existing SHA-256 response ETag changes with the new payload; an old `If-None-Match` receives the corrected JSON, while a current ETag receives 304. The marker is neither an editor input nor a runtime response field.

Runtime always emits `community.quickActions.friends.foreground`, `community.quickActions.genes.foreground`, `community.quickActions.circles.foreground`, and `community.quickActions.search.foreground` as `{ light: "#FFFFFF", dark: "#FFFFFF" }`. These roles are consumed only by the title and Open text labels. Illustration/icon rendering, tile backgrounds, fixed Genes accents, semantic colors, and every other override remain unchanged. Runtime export does not rewrite stored editor configuration.

The shared visual identity editor has three draft sections: general identity, three main colors, and four counterpoints. A custom counterpoint stays fixed when the primary changes; automatic ones follow the existing hue calculation. Restoring an automatic value uses the current primary. Only Apply requests the override plan and commits the resulting palette to the form; Cancel discards the draft, and a failed calculation leaves the previously applied palette intact. The normal app save persists these applied choices.

Automatic palette application stores its automatic result separately in optional `advancedConfiguration.generatedColorOverrides`. The next application compares each current light/dark value with that saved baseline: unchanged generated values are recalculated, manual values and alpha are retained, and an explicitly removed generated appearance continues using its native fallback. Contrast is checked again after merging manual edits: automatic ink or gradient stops adapt around locked manual values, and those automatic corrections enter the baseline. An impossible combination of locked colors fails Apply without overwriting those colors. This provenance is validated and persisted with the editor configuration, but is never included in the mobile runtime JSON. Existing apps without provenance recognize exact results from the frozen v5 calculator and from the current calculator, the earlier contrast treatment, the superseded broad surface-darkening treatment, the pre-restoration Genes treatment, and the previous quick-action background treatment under their previous palette; unknown values remain manual. Historical HSL defaults and both superseded OKLCH variants are also recognized when an older configuration omitted counterpoint seeds.

Manual counterpoints use the existing four camelCase fields under `colors`, with no extra persistence flags. Request validation, palette planning, SDK normalization, stored reads and runtime export preserve supplied values. Missing counterpoints use the original vivid HSL calculation: rotations of ±45° and ±75°, saturation at least 85%, and lightness bounded to 48–58%. Only a result in the orange range moves by fixed 40° hue steps; the other counterpoints keep their original colors. The editor shows each automatic color's actual rotation. Runtime continues exposing only the two declared near counterpoints; far counterpoints supply their existing tonal override flows.

Both creation wizards and the edit screen share catalog v8 (698 roles, 21 declared contrast relationships). Synchronize the complete native source and SDK allowlist together with `node scripts/sync-publisher-app-color-catalog.mjs [path-to-CUSTOM_APP_COLORS.json]`. Each light/dark family is transformed continuously: relative hue spacing and chroma ratios are retained, shade lightness changes monotonically around its anchor, and environmental backgrounds, lighting and functional ink retain their original lightness. Generated anchors reserve shade headroom for black/white seeds. The selected base palette and counterpoints stay unchanged; generated structural fill roles use darker shades only for eligible, genuinely bright yellow/green/cyan tones. Existing ochre, muted and dark shades remain unchanged. Quiet modes and semantic states are protected independently, deep dark foundations remain native, and unchanged modes are omitted so platform-specific defaults and exact native opacity survive. Illustration destinations keep their native brand/counterpoint resolver unless manually overridden. Existing foreground contrast checks retain their scoped light/dark relationships and manual-color rules. The selective bright-fill correction does not impose a global opaque contrast target against hypothetical white material. Manual overrides are merged afterwards without modifying their values. Only genuinely bright yellow, green and cyan fills in registered buttons, tabs and pills receive the additional same-hue treatment (HSV hue 45–195°, saturation at least 0.1, opaque white contrast below 2.5). It targets the native 3:1 opaque treatment, bounded by unchanged darker neighbors rather than forcing every stop to 4.5:1. It does not lower already-dark stops simply because another stop is bright, and keeps stop ordering, hue relationships and alpha. Manual light/dark fills and foregrounds remain locked; automatic colors adapt around them or Apply reports an impossible contrast combination.

The Community quick-action backgrounds use an explicit row order: Friends starts from `colors.primary`, Genes from `colors.secondary`, Circles from `colors.tertiary`, and Search from `colors.counterpointClockwise`. The principal remains its own center; the other three receive a gentle 12% principal chromatic-axis mix in OKLab while retaining their selected lightness. The chromatic mix limits hue drift to approximately 6° and chroma loss to 10% before final byte rounding, so opposing hues cannot turn the chosen colors into washed or unrelated tones. Each tile derives a short, consistent gradient and lower rim from that center, instead of carrying the old purple/cyan template's hue spacing. The existing narrowly scoped bright yellow/green/cyan treatment remains local; already dark or ochre tones do not receive blanket darkening. Native highlights already supply the shared gloss. Manual per-appearance background overrides, opaque-white text, original illustrations, and the fixed Genes flow inside the destination retain their existing behavior.

The fixed Genes tonal flow preserves its historical vivid identity independently of the selected brand. Its sixteen accent and gradient roles keep the original fixed-family output, including `community.genes.primary` light `#00A88A`, without the later automatic contrast corrections dimming them. Surrounding surfaces, functional ink, unrelated flows, and explicit manual light/dark overrides retain their existing behavior. Reapplying an older generated palette recognizes the previous dimmed Genes result and restores the automatic accents while preserving manual Genes colors and alpha.

The backoffice publisher and GOD MODE creation wizards contain four steps: platform, features, colors, and icon. Creation requires no terms acceptance and records no signature. The final CTA runs four ordered operations: create the base app, calculate the palette overrides, update the app with the full advanced configuration, and create its testing identifier. The final identifier command sets new apps to `active_for_testing`; it never promotes a newly created app to `active`. One progress dialog reflects completed responses. Retries retain acknowledged checkpoints; palette, update, or identifier failures do not create another app or publish an incomplete configuration. Only confirmed testing activation triggers the green creation celebration and the notification explaining that the app is ready to test.

The edit screen shows `Publicar mi app` only for a saved `active_for_testing` app with a current identifier and no unsaved changes. Its `/sign-terms-and-conditions` page contains only the publication review and terms step. Acceptance sends `termsAccepted: true` and `expectedUpdatedAt` to the dedicated publication command. One transaction validates the saved configuration, records the signature, immediately changes the canonical status to `active_waiting_for_payment`, advances `runtimeRevision`, and updates the catalog and status counts. Concurrent or stale edits cannot revert that transition. The publication celebration appears only after the response confirms the new status and signature. The separate publication notification explains the request to upload the app and coordinate payment. Successful retries reuse the signed state without sending another notification.

`active_for_testing`, `active_waiting_for_payment`, `active_waiting_for_upload`, and `active` remain distinct persisted statuses. All four allow runtime access, catalog availability, identifier reuse, revision updates and deactivation. Existing active apps retain their status, including when a legacy identifier is replaced. New catalog snapshots include separate testing, waiting-for-payment, and waiting-for-upload counts; older snapshots remain readable with a zero count for each missing additive status only when no item uses that status. Runtime JSON retains its existing `published` status. Waiting for upload is an operator-selected state; signing still changes an app to waiting for payment and does not automatically advance it to upload.

All current states appear as labels. Only GOD MODE exposes `Cambiar estado`, which opens a single-value picker; the publisher portal has no manual status control. Server-side admin updates require bootstrap access, ordinary publisher updates reject a submitted status, and publishers cannot manually deactivate the identifier to change the state. Automatic creation activation and terms-signing transitions retain their existing behavior.

GOD MODE uses `POST` / `PUT /admin/publisher-app-configs/organizations/:organizationId` and `POST /admin/publisher-app-configs/organizations/:organizationId/identifier`. Publication uses `POST /admin/publisher-app-configs/:configId/sign-terms-and-conditions`. All these commands require bootstrap access. The publisher portal uses its existing scoped `/publisher-app/config` commands and `POST /publisher-app/config/sign-terms-and-conditions` for publication. Ordinary updates preserve the original terms acceptance and audit identity; a plain status update cannot bypass signing to enter `active_waiting_for_payment`.

The GOD MODE app list supports individual deletion and selection of multiple loaded apps. `DELETE /admin/publisher-app-configs/:configId` requires bootstrap access and `{ expectedUpdatedAt }` from the confirmed list item. A changed or recreated config returns 409; an already absent config succeeds idempotently. Each deletion atomically removes its `app_configs` document and catalog entry and updates the catalog counters. It accepts every app status and either publisher kind without changing the publisher portal's pending-revision-only deletion rule. Publisher records, authored content, shared catalog icons and permanent identifier reservations remain intact. The UI processes the confirmed selection sequentially, reports each outcome, and reloads pagination from the first page so deleted cursor documents cannot break subsequent loading.

`custom_apps_snapshot/simple` keeps the existing catalog schema and `image` field, but newly written catalog images are HTTPS references rather than embedded data URLs. Each inline image is stored once in `custom_app_icons/{sha256}`, with exactly `contentType` and `base64` string fields. The hash is SHA-256 of the original complete data URL; documents are immutable by content identity and bounded by the existing 900,000-character image limit. Original app and publisher icon fields stay intact.

Incremental catalog transactions compact every legacy inline image and write the referenced icon documents atomically with the catalog update. Full snapshot refreshes persist deduplicated icons in bounded groups before writing the compact catalog. This prevents accumulated images from exceeding Firestore's aggregate document limit.

`GET /publisher-app/icon?hash=<64 lowercase hex characters>` serves only those catalog icon bytes, with an immutable cache policy, cross-origin image embedding, MIME validation, hash verification, and a sandboxed content security policy. Missing hashes return 404 and invalid parameters return 400. App configurations and all app commands remain authenticated. No new Firebase project or storage bucket is required at startup.
