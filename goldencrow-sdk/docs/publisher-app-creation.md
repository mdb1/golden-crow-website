# Publisher app creation

Runtime `branding.colors` preserves `advancedConfiguration.semanticColors` when supplied, or the existing nine-color semantic derivation otherwise, and appends each normalized `config.colors.counterpointClockwise` / `config.colors.counterpointAnticlockwise` only when available. The nine semantic fields remain required; both counterpoints are optional six-digit hex fields in the runtime producer type and OpenAPI response contract. A missing counterpoint is omitted without synthesizing a replacement, allowing native clients to retain canonical purple `#8A4BF7` or cyan/turquoise `#19D7E1`. Manual light/dark `colorOverrides` and automatic palette policies are unchanged.

An existing active app is republished atomically on its first runtime read after this contract update: `runtimeRevision` increases by one and the server-only `runtimeColorContractVersion` publication marker is stored in `app_configs`. New activations and subsequent active saves already publish the current contract. Publisher exports, GOD MODE exports, and public runtime reads share this publication check, so repeated reads keep the same revision. The existing SHA-256 response ETag changes with the new payload; an old `If-None-Match` receives the corrected JSON, while a current ETag receives 304. The marker is neither an editor input nor a runtime response field.

The shared visual identity editor has three draft sections: general identity, three main colors, and four counterpoints. A custom counterpoint stays fixed when the primary changes; automatic ones follow the existing hue calculation. Restoring an automatic value uses the current primary. Only Apply requests the override plan and commits the resulting palette to the form; Cancel discards the draft, and a failed calculation leaves the previously applied palette intact. The normal app save persists these applied choices.

Manual counterpoints use the existing four camelCase fields under `colors`, with no extra persistence flags. Request validation, palette planning, SDK normalization, stored reads and runtime export preserve supplied values. Missing counterpoints continue to receive the calculated defaults in the editor/config model. Runtime continues exposing only the two declared near counterpoints; far counterpoints supply their existing tonal override flows. The color derivation and override-planning algorithms are unchanged.

The backoffice publisher and GOD MODE creation wizards run four ordered operations after terms acceptance: create the base app, calculate the palette overrides, update the app with the full advanced configuration, and create its active identifier. One progress dialog reflects completed responses. Retries retain acknowledged checkpoints; palette, update, or identifier failures do not create another app or publish an incomplete configuration.

GOD MODE uses `POST` / `PUT /admin/publisher-app-configs/organizations/:organizationId` and `POST /admin/publisher-app-configs/organizations/:organizationId/identifier`. All three commands require bootstrap access. The publisher portal uses its existing scoped `/publisher-app/config` commands. Updates preserve the original terms acceptance and audit identity.

`custom_apps_snapshot/simple` keeps the existing catalog schema and `image` field, but newly written catalog images are HTTPS references rather than embedded data URLs. Each inline image is stored once in `custom_app_icons/{sha256}`, with exactly `contentType` and `base64` string fields. The hash is SHA-256 of the original complete data URL; documents are immutable by content identity and bounded by the existing 900,000-character image limit. Original app and publisher icon fields stay intact.

Incremental catalog transactions compact every legacy inline image and write the referenced icon documents atomically with the catalog update. Full snapshot refreshes persist deduplicated icons in bounded groups before writing the compact catalog. This prevents accumulated images from exceeding Firestore's aggregate document limit.

`GET /publisher-app/icon?hash=<64 lowercase hex characters>` serves only those catalog icon bytes, with an immutable cache policy, cross-origin image embedding, MIME validation, hash verification, and a sandboxed content security policy. Missing hashes return 404 and invalid parameters return 400. App configurations and all app commands remain authenticated. No new Firebase project or storage bucket is required at startup.
